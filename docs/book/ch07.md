### 7.2.2 RDMA 连接超时

RDMA（Remote Direct Memory Access）是 IB 和 RoCE 网络的核心传输方式，允许 GPU显存直接通过网卡进行跨节点传输，绕过 CPU 和操作系统内核。RDMA 连接超时通常表现为 NCCL通信挂起或训练任务长时间无响应。RDMA 超时排查流程：RDMA 超时常见原因与解决方案：PFC（Priority Flow Control）死锁：在 RoCE v2 网络中，PFC配置不当可能导致头端阻塞（Head-of-Line Blocking），表现为间歇性 RDMA超时。解决方案是确保所有交换机端口配置一致的 PFC 阈值，推荐 XOFF 阈值设置为总缓冲区的50%。

ECN（Explicit Congestion Notification）未启用：RoCE v2 依赖 DCQCN 拥塞控制算法，需要ECN 配合。如果交换机未启用ECN，拥塞时不会触发速率降低，导致缓冲区溢出和丢包。解决方案是在所有交换机端口启用ECN，设置 ECN 标记阈值为缓冲区深度的 20%。MTU 不匹配：RDMA 要求端到端 MTU 一致。如果某个链路的 MTU小于其他链路，大包会被丢弃。解决方案是统一所有端口的 MTU 为 9000（Jumbo Frame）或 IB 的4096。Subnet Manager 异常：IB 网络依赖 Subnet Manager（SM）进行路由配置。

如果 SM异常，新加入的节点无法获得路由信息。解决方案是部署冗余 SM（主备模式），监控 SM 状态。

## 7.3 存储故障排查

AI 训练和推理对存储系统有着极高的要求：训练数据加载需要高吞吐量（通常 > 50 GB/s聚合带宽），Checkpoint 写入需要低延迟和大块顺序写能力，模型推理需要快速加载数十 GB的模型文件。存储系统的任何性能下降或故障都会直接影响 AI 工作负载的效率。

### 7.3.1 分布式文件系统性能下降

AI 集群常用的分布式文件系统包括NFS（简单但性能有限）、Lustre（高性能但运维复杂）、GPFS/Spectrum Scale（IBM商业方案）、以及基于对象存储的 FUSE 挂载方案（如 JuiceFS、GooseFS）。以下以 Lustre为例说明性能排查方法。Lustre 性能排查命令：分布式文件系统性能下降的常见原因：元数据瓶颈：训练数据集包含数百万个小文件（如 ImageNet 的 150万张图片），每次打开文件都需要元数据操作。如果 MDT 性能不足，文件打开延迟会从正常的< 1ms 上升到 100ms+。

解决方案：使用大文件 + 条带化存储，或将小文件打包为TFRecord/WebDataset 格式。条带化配置不当：Lustre 的条带化（striping）配置直接影响读写性能。条带数过少会导致单OST 过载，条带数过多会增加元数据开销。推荐配置：对于大文件（> 1GB），条带数 = OST数量的 50%-100%，条带大小 = 1MB 或 2MB。客户端缓存未命中：Lustre 客户端有 Page Cache 和 DNE（Distributed NamespaceEntry）缓存。如果工作集远大于客户端内存，缓存命中率下降会导致大量后端IO。

解决方案：增加客户端内存或使用 SSD 作为缓存层。网络拥塞：分布式文件系统的后端网络与训练通信网络共享物理链路时，会产生拥塞。解决方案：存储网络与训练网络物理隔离。

### 7.3.2 Checkpoint 写入失败

Checkpoint 是大规模训练的"保险绳"——它保存了训练过程中模型参数、优化器状态和学习率调度器的快照，使得训练中断后可以从最近的 Checkpoint 恢复，而不是从头开始。Checkpoint写入失败或过慢是大规模训练中的常见问题。Checkpoint 写入性能基准：Checkpoint 写入失败的常见原因：存储空间不足：Checkpoint 文件巨大，如果存储配额或物理空间不足，写入会失败。解决方案：设置存储空间监控，保留至少 3 个最新 Checkpoint 的空间。写入超时：当 Checkpoint文件过大而存储带宽不足时，写入时间超过框架超时限制。

解决方案：使用异步 Checkpoint（如PyTorch 的 torch.distributed.checkpoint 异步模式），将写入操作放到后台线程。文件系统锁冲突：多个节点同时写入同一个 Checkpoint文件时可能产生锁冲突。解决方案：使用分布式 Checkpoint 方案，每个 rank写入独立的文件，然后通过 manifest 文件管理。IO 调度冲突：Checkpoint 写入与训练数据读取竞争存储带宽。解决方案：将 Checkpoint写入到独立的存储路径或存储系统。

### 7.4.2 梯度爆炸/消失的 Infra 层面原因

梯度爆炸（Gradient Explosion）和梯度消失（GradientVanishing）通常是算法层面的问题（如网络结构、学习率设置、权重初始化等），但 Infra层面的问题也可能导致或加剧这些现象。Infra 层面导致梯度异常的原因：混合精度训练中的溢出：使用 FP16/BF16 混合精度训练时，如果 GPU 的 Tensor Core存在硬件问题，可能导致计算结果溢出。A100 的 FP16 Tensor Core 峰值为 312TFLOPS，如果实际计算中某些 Tensor Core出现间歇性错误，会导致部分梯度值异常。

诊断方法：使用 nvidia-smi 检查 ECC 错误，使用 GPUBurn 进行压力测试。梯度同步中的精度损失：在使用 NCCL AllReduce进行梯度同步时，如果网络出现丢包重传，可能导致梯度数据损坏。NCCL 默认使用 CRC校验来保证数据完整性，但如果校验逻辑本身出现问题（如驱动Bug），可能导致错误的梯度被使用。诊断方法：设置 NCCL_DEBUG=INFO查看通信日志，比较同步前后的梯度范数。Gradient Accumulation 步骤数错误：当使用梯度累积（Gradient Accumulation）来模拟更大的batch size 时，如果某些 micro-batch 因为数据加载失败而被跳过，累积的梯度会偏小，等效于学习率降低。

诊断方法：在训练代码中记录每个 micro-batch 是否成功加载。ZeRO 优化器状态分片错误：在使用 DeepSpeed ZeRO-3 或 FSDP 时，优化器状态被分片到多个GPU 上。如果某个 GPU出现硬件错误导致其分片的数据损坏，会影响全局的参数更新。诊断方法：检查各 GPU的优化器状态范数是否一致。

### 7.4.3 大规模训练中断恢复

大规模训练（尤其是预训练）通常需要连续运行数周甚至数月。在此期间，硬件故障、网络中断、电力波动等都可能导致训练中断。建立高效的训练中断恢复机制是 Infra 团队的核心职责之一。训练中断恢复策略：实际案例：某国央企使用 512 卡 A100 集群训练一个 13B 参数的行业模型，训练预计需要 45天。在第 23 天时，一次机房电力波动导致 8 个节点同时宕机。由于采用了同步 Checkpoint 策略（每500 步保存一次，约每 2 小时），训练从最近的 Checkpoint 恢复。但恢复过程中发现：(1) Checkpoint加载耗时 25 分钟（350GB 的 Checkpoint 文件从 Lustre 加载）；

### 7.4.4 多节点训练死锁

多节点训练死锁是指两个或多个节点互相等待对方发送消息，导致训练任务永久挂起。死锁是分布式训练中最棘手的问题之一，因为它不会导致任务崩溃，只是让任务"卡住"，如果不设置超时检测，可能长时间不被发现。死锁的常见原因：集合通信拓扑不匹配：当不同 rank 对集合通信的拓扑理解不一致时（如某些 rank 认为自己在Ring 中，而另一些认为自己在 Tree 中），会导致消息发送和接收不匹配。解决方案：确保所有rank 使用相同的 NCCL 版本和通信拓扑配置。条件分支导致的通信不对称：当模型代码中存在基于 rank 的条件分支（如 if rank ==0），且分支内部包含集合通信操作时，会导致部分 rank执行通信而另一些不执行。

解决方案：确保所有 rank都执行相同的集合通信操作，或使用点对点通信替代。梯度累积步数不一致：当某些 rank 因为数据加载失败而跳过了 micro-batch，导致不同 rank的梯度累积步数不同，最终的 AllReduce操作会死锁。解决方案：使用同步屏障（barrier）确保所有 rank 完成相同数量的 micro-batch。网络分区：当网络出现分区（部分节点之间无法通信）时，跨分区的集合通信会死锁。解决方案：部署网络分区检测，在训练开始前验证全连接连通性。死锁检测与预防：

### 7.5.1 推理服务 OOM

推理服务 OOM（Out of Memory）是推理部署中最常见的故障。与训练不同，推理服务需要同时服务多个并发请求，内存管理更加复杂。推理服务显存占用分析（以 LLaMA-70B 为例）：推理 OOM 的常见原因与解决方案：KV Cache 无限增长：长序列请求的 KV Cache 可能占用大量显存。如果没有限制最大序列长度，一个超长请求就可能耗尽显存。解决方案：设置 max_sequence_length 限制，使用PagedAttention（vLLM）或 Ring Attention 管理 KV Cache。

并发请求过多：高并发下，每个请求都需要独立的 KV Cache和激活值空间。如果并发数超过显存容量，会导致 OOM。解决方案：使用动态batching，根据显存使用情况动态调整并发数。显存碎片化：频繁的显存分配和释放会导致碎片化，即使总可用显存足够，也可能因为无法分配连续内存而 OOM。解决方案：使用显存池化管理（如 vLLM 的PagedAttention），预分配显存块。模型权重未卸载：当使用 CPU offloading 时，如果卸载逻辑有Bug，可能导致部分权重同时存在于 CPU 和 GPU内存中。解决方案：检查模型加载逻辑，确认权重只存在于预期的设备上。

### 7.5.3 推理吞吐量下降

推理吞吐量（通常以 tokens/s 或 requests/s 衡量）下降意味着服务容量降低，在请求量不变的情况下会导致延迟增加。吞吐量下降通常是渐进性的，容易被忽视。推理吞吐量下降的常见原因：GPU 降频：如前文所述，GPU温度过高或供电不足会导致降频，直接降低计算性能。解决方案：监控 GPU时钟频率，设置降频告警。Batch 效率下降：当请求的序列长度分布发生变化（如大量长文本请求），batch 内的 padding比例增加，有效计算量下降。解决方案：使用 continuous batching（如vLLM、TensorRT-LLM），根据序列长度动态组 batch。

显存带宽瓶颈：Decode 阶段是 memory-bound 的，显存带宽直接限制 token 生成速度。如果GPU 降频导致显存频率下降，或者显存出现 ECC 错误导致有效带宽降低，都会影响吞吐量。解决方案：监控显存带宽利用率，确保显存工作正常。CPU 瓶颈：推理服务中的 Tokenizer、调度器、后处理等组件运行在 CPU 上。如果 CPU负载过高，会成为瓶颈。解决方案：监控 CPU 使用率，必要时增加 CPU 核心数或优化Tokenizer（如使用 Rust 实现的快速 Tokenizer）。

### 7.6.3 案例：某国央企集群利用率从 20% 提升到 80%

### 7.7.3 故障自愈系统

故障自愈系统的目标是在检测到故障后，无需人工介入即可自动完成故障隔离、任务迁移和恢复。以下是故障自愈系统的核心能力：GPU 故障自愈：检测到 GPU 故障（如UCE、掉卡）后，自动将故障节点标记为不可调度，触发训练任务从最近的 Checkpoint恢复（排除故障节点），并通知运维团队更换硬件。网络故障自愈：检测到网络链路故障后，自动切换到备用链路（如果有），并重新配置 NCCL通信拓扑。如果故障无法自动恢复，触发训练任务优雅降级（减少数据并行度）。存储故障自愈：检测到存储性能下降后，自动将数据读取切换到备用存储路径，并触发数据预取以弥补性能损失。

推理服务自愈：检测到推理实例异常后，自动将流量切换到健康实例，并重启异常实例。如果异常实例无法恢复，自动扩容新实例。
