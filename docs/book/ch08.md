## 8.3 推理侧极致优化

推理优化是字节跳动 AI Infra 的核心竞争力之一。作为 C 端产品，豆包大模型需要在保证用户体验的前提下，将推理成本压到最低。以下是字节在推理侧的核心优化策略。

### 8.3.1 PD 分离架构实现

PD 分离（Prefill-Decode Disaggregation）是字节跳动推理架构的核心创新之一。其核心思想是将Prefill（首 token 计算，compute-bound）和 Decode（后续 token生成，memory-bound）两个阶段部署在不同的 GPU 实例上，分别进行优化。PD 分离架构详解：PD 分离的优势：硬件选型优化：Prefill 阶段是 compute-bound 的，适合使用高算力 GPU（如 H100，FP16 算力989 TFLOPS）；Decode 阶段是 memory-bound 的，适合使用高显存带宽 GPU（如 H100，HBM3带宽 3.35 TB/s）。

PD 分离允许为两个阶段选择不同配置的 GPU。资源利用率提升：Prefill 和 Decode 的资源需求不同（Prefill 需要高算力，Decode需要大显存），混合部署会导致资源浪费。分离后可以分别优化，GPU 利用率提升 30-50%。独立扩缩容：Prefill 和 Decode 的负载特征不同（Prefill 随请求量波动，Decode随序列长度和并发数变化），分离后可以独立扩缩容，避免过度配置。PD 分离的挑战与解决方案：KV Cache 迁移开销：Prefill 完成后，KV Cache 需要从 Prefill 实例迁移到 Decode实例。

对于长序列（如 32K tokens），KV Cache 大小可达数 GB，迁移耗时可能超过100ms。解决方案：使用 RDMA 直接传输 KV Cache，利用 GPUDirect RDMA 绕过 CPU；使用 KVCache 压缩（如量化为 FP8）减少传输数据量。调度复杂度增加：PD 分离需要协调 Prefill 和 Decode 实例的调度，确保 KV Cache迁移的时序正确。解决方案：开发专用的 PD 调度器，维护 Prefill 和 Decode 实例的状态映射。

### 8.3.3 动态 Batch 策略

字节跳动使用 Continuous Batching（连续批处理）技术，取代传统的静态 Batching，大幅提升 GPU利用率。静态 Batching vs Continuous Batching：Continuous Batching 的关键技术：PagedAttention：将 KV Cache 分成固定大小的"页"（如 16 tokens一页），按需分配和释放，避免显存碎片化。这是 Continuous Batching 的核心支撑技术。动态调度：调度器每完成一个 token 的生成，就检查是否有新请求可以加入当前batch，或者是否有请求已经完成可以释放资源。

优先级队列：支持请求优先级调度，如 VIP 用户或高优先级任务可以优先获得计算资源。

### 8.3.4 超高 QPS 保障机制

豆包大模型需要支撑极高的 QPS（Queries Per Second），峰值可能达到数十万QPS。以下是保障超高 QPS 的核心机制：多区域部署：在华北、华东、华南等多个区域部署推理集群，用户请求就近路由到最近的集群，减少网络延迟并分散负载。自动扩缩容：基于请求队列长度和 GPU 利用率，自动扩容或缩容推理实例。扩容时间目标 < 3分钟（从触发到新实例就绪）。请求限流与降级：当请求量超过系统容量时，触发限流（RateLimiting）和降级策略（如返回缓存结果或简化模型），确保系统不崩溃。故障转移：当某个推理实例或集群出现故障时，自动将流量切换到健康实例/集群，确保服务可用性 > 99.9%。

### 8.4.1 "算力堆规模 + 软件极致压榨"策略

字节跳动的技术路线可以概括为"算力堆规模 + 软件极致压榨"：在硬件层面追求集群规模的极致扩张，在软件层面通过极致优化榨取每一分算力。这一策略在国内外科技巨头中独树一帜——与阿里巴巴的"全栈自研"、华为的"国产化替代"、Google 的"TPU自研"不同，字节选择了"不造芯片，把通用硬件用到极致"的路线。这一策略的逻辑基础：规模效应：大模型的性能与训练数据量和模型参数量强相关（ScalingLaw）。更大的集群可以训练更大的模型，处理更多的数据，从而获得更好的模型性能。根据Chinchilla Scaling Law，最优训练策略是让模型参数量和训练 tokens数同步增长。

对于一个千亿参数的模型，至少需要万亿 tokens的训练数据，这需要万卡级集群运行数月。成本摊薄：集群的固定成本（网络设备、管理节点、存储系统等）随着 GPU数量的增加而被摊薄。以 IB 网络为例，一个 1000 卡集群和 10000 卡集群所需的 IB交换机管理节点数量相差不大，但 10000 卡集群的单卡网络成本仅为 1000 卡的1/5-1/3。据行业分析，万卡集群的单卡综合成本（含网络、存储、管理）比百卡集群低 30-50%。软件优化的杠杆效应：在万卡规模下，1% 的效率提升意味着 100 张 GPU 的等效算力节省。

以H100 约 20 万元/张计算，100 张 GPU 价值约 2000 万元。如果软件优化可以将 MFU 从 40% 提升到50%（提升 25%），在万卡集群中等效于节省 2500 张 GPU，价值约 5亿元。因此，字节在软件优化上投入了大量顶级工程资源，据报道其推理优化团队超过 200 人。"软件极致压榨"的具体体现：与竞争对手的策略对比：字节的"不造芯片"策略与以下几家形成鲜明对比：vs Google：Google 投入大量资源自研 TPU，目前已发展到第五代（TPU v5p）。TPU 在大规模训练中表现出色，但需要重新适配软件生态。

字节认为，自研芯片的投入产出比不如将资源集中在软件优化上。vs 阿里巴巴：阿里自研含光芯片和倚天 CPU，追求全栈自主可控。字节则认为，在 NVIDIA生态足够成熟的情况下，自研芯片的边际收益有限。vs 华为：华为自研昇腾芯片是出于供应链安全的考虑（美国制裁）。字节虽然也面临供应链风险，但通过多元化供应商（NVIDIA、AMD）和提前囤货策略来应对，而非自研芯片。核心洞察：字节的策略本质上是一种"比较优势"选择——在 NVIDIA GPU持续迭代的背景下，自研芯片很难在性能上超越NVIDIA，但软件优化的空间是无限的。

将有限的工程资源投入到 ROI更高的软件优化上，是更理性的商业决策。但这一策略的风险在于：如果 NVIDIA的供应链出现严重问题（如全面禁止对华出口），字节将面临"无芯可用"的困境。

### 8.4.2 重集群调度与流量工程

字节跳动在集群调度和流量工程方面的投入，在国内互联网公司中可能是最大的。这与其 C端业务的特性密切相关——豆包 App 的日活超过 1 亿，任何调度不当或流量管理失误都会直接影响上亿用户体验。以下是字节在集群调度和流量工程方面的核心能力：（1）智能 GPU 调度器字节自研的 GPU 调度器是其 Infra 体系的核心组件之一。该调度器需要同时管理数万张GPU，处理数千个训练和推理任务的资源请求。调度器的核心能力包括：（2）流量工程体系推理服务的流量工程是保障豆包用户体验的关键。字节的流量工程体系包括以下层次：全局流量管理（GSLB）：根据用户的地理位置和各地域集群的负载情况，将请求路由到最优的数据中心。

例如，北京用户的请求优先路由到华北数据中心，上海用户优先路由到华东数据中心。集群内负载均衡：在单个数据中心内，根据各推理实例的实时负载（GPU利用率、请求队列长度、KV Cache使用率），将请求分配到最空闲的实例。使用加权最少连接（Weighted LeastConnections）算法，确保负载均匀分布。请求级路由：对于 PD 分离架构，请求首先路由到 Prefill 实例，完成首 token 计算后，KV Cache迁移到 Decode 实例，后续 token 由 Decode 实例生成。路由系统需要协调 Prefill 和 Decode实例的配对关系。

流量镜像：在新版本上线前，将部分流量（通常 1-5%）镜像到新版本实例，对比新旧版本的性能指标（延迟、错误率、输出质量），确认无问题后再逐步切换全量流量。（3）弹性伸缩策略字节的弹性伸缩系统基于多维度指标进行决策，而非简单的 CPU/GPU利用率阈值。伸缩决策考虑的因素包括：请求队列长度：当等待队列中的请求数超过阈值时，触发扩容。P99 延迟：当 P99 延迟超过 SLA 阈值时，触发扩容。流量预测：基于历史流量模式（如每日/每周的周期性波动）和实时趋势，预测未来 5-15分钟的流量，提前扩容。成本约束：在满足 SLA 的前提下，尽量减少 GPU 使用数量。

当流量下降时，延迟缩容（等待5-10 分钟确认流量确实下降后再缩容），避免频繁伸缩带来的开销。

### 8.7.1 私有化方案薄弱

### 8.7.3 内网隔离场景不适合

某些企业（如军工、涉密单位、关键基础设施运营商）要求 AI系统在完全隔离的内网中运行，无法访问互联网。字节跳动的 AI 平台依赖互联网连接进行 API调用、模型更新和运维支持，无法在这类场景中使用。内网隔离场景的特殊要求：离线运行：AI 系统必须能够在完全断网的环境下运行，包括模型推理、微调和监控。安全审计：所有操作必须记录完整的审计日志，支持事后追溯。供应链安全：硬件和软件必须经过安全审查，确保没有后门和漏洞。自主运维：企业必须能够自主完成系统的运维和升级，不依赖外部支持。在这些场景下，企业需要选择支持完全私有化部署的方案（如阿里云的行业私有 AI云、华为的昇腾全栈方案），而非依赖公有云服务。
