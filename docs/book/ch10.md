### 10.1.3 "克制型算力策略"核心原则

腾讯 AI Infra 最显著的特征是其"克制型算力策略"。这一策略的核心原则可以概括为以下四条，每一条都有具体的数据和案例支撑。原则一：需求驱动，不做冗余储备与字节跳动"先建万卡集群再找场景"的策略相反，腾讯始终坚持"先有明确业务需求，再按需扩展算力"的原则。以 2024 年为例，腾讯新增 GPU 采购量约 2,000 张，而同期字节新增超过 15,000张。这种策略的好处是避免了大量 GPU 闲置——据行业估算，国内大厂平均 GPU 利用率仅为30-40%，字节约 40-50%，阿里约 50-60%，而腾讯通过精细化调度将利用率控制在 55-65%水平。

虽然绝对值不算极高，但相比行业平均已属优秀，且避免了过度投资带来的折旧压力。以 H800为例，单卡采购成本约 12-15 万元，如果闲置一年，折旧损失约 3-4 万元/卡。腾讯少采购 10,000 张GPU，仅折旧一项就节省 3-4 亿元/年。原则二：软件优化优先于硬件堆叠腾讯在 AI Infra 领域的投入结构非常有特点：软件研发团队规模约为硬件采购预算的 1.5倍（按人力成本计）。腾讯 AI Infra 软件团队超过 300 人，年度人力成本约 3-4亿元，而年度硬件采购预算约 2-3 亿元。这种"重软件、轻硬件"的投入结构，使得腾讯可以通过软件优化大幅降低对硬件的依赖。

具体投入方向包括：训练框架优化：自研 Angel 分布式训练框架，团队 50+ 人，通过 3D 并行策略（数据并行 +模型并行 + 流水线并行）将千卡训练的线性加速比提升至 0.85 以上（行业平均0.70-0.75），等效于在同等硬件上训练速度提升 15-20%推理加速：自研 BladeLLM 推理引擎，团队 30+ 人，通过 PagedAttention、ContinuousBatching、Speculative Decoding 等技术，将推理吞吐量提升 2.5-3 倍，等效于节省 60-70% 的推理GPU显存优化：通过 Offload 技术将部分 KV Cache 卸载到 CPU 内存，在推理阶段节省 30-40% 的GPU 显存，使得同等硬件可以处理更长的上下文，或支持更多的并发请求网络优化：自研智能网卡（DPU）卸载 RDMA 协议栈处理，团队 40+人，将网络延迟从软件方案的 8-10μs 降低到 2-3μs，同时释放 2-4 个 CPU 核心，等效于节省10-15% 的服务器成本原则三：存量资源最大化复用腾讯拥有国内互联网公司中规模最大的存量 GPU 资源——这些 GPU原本用于游戏渲染、视频转码、推荐系统等业务。

这种配置下，节点内通信走NVLink（900GB/s 带宽），节点间通信走 RoCE（200Gbps 带宽），通信开销占比控制在 15%以内。相比之下，如果盲目扩大到万卡规模，节点间通信开销将上升到30-40%，反而导致训练效率下降。实测数据显示，腾讯从 256 卡扩展到 2,048 卡时，线性加速比为0.85，即训练速度提升到原来的 8 倍（理论最大值也是 8 倍），而行业平均线性加速比仅为 0.70-0.75。（2）梯度压缩与异步通信腾讯自研的梯度压缩算法可以将通信数据量压缩到原始大小的 1/4-1/8，同时保持训练精度损失在0.5% 以内。

具体实现：采用 Top-K 稀疏化策略，仅传输梯度中绝对值最大的 10-25%的参数，其余参数置零；使用 Error Feedback机制补偿截断误差，将上一轮被截断的误差累积到下一轮的梯度中；结合异步All-Reduce，将通信与计算重叠，进一步隐藏通信延迟。实测数据显示，在 2,048 卡集群上训练 500BMoE 模型，开启梯度压缩后的训练速度仅比不压缩慢 3-5%，但网络带宽需求降低了70%，这意味着可以使用成本更低的 200Gbps RoCE 网络替代 400Gbps InfiniBand，节省网络建设成本约40-50%。

（3）Checkpoint 优化大规模训练中最怕的是节点故障导致训练中断。在万卡集群中，单节点故障的概率约为每天 1-2次（按单节点 MTBF 约 5,000 小时计算），每次故障如果处理不当，可能导致 30-60分钟的训练中断。腾讯的 Checkpoint 策略包括三个层面：异步Checkpoint——训练不暂停，后台线程将模型状态写入分布式存储，对训练速度的影响仅 1-2%；增量Checkpoint——仅保存变化的参数（优化器状态），每次 Checkpoint 数据量从全量的 2-3TB 降低到200-500GB；

高频 Checkpoint——每 30 分钟一次（行业通常 1-2 小时），故障恢复时间从 30-60分钟缩短到 5 分钟以内。综合效果：年度训练中断时间从行业的 200-300 小时降低到 30-50小时，等效于多出 150-250 天的有效训练时间。

### 10.2.2 推理优化与智能网卡

截至 2025年初，已部署超过 2,000 张智能网卡，覆盖 80% 的推理集群。智能网卡的核心功能包括三个方面：RDMA 协议栈卸载：将 RoCE v2 的协议处理（包括包组装、拥塞控制、错误重传等）从 CPU卸载到网卡硬件，CPU 开销从 15-20% 降低到 2-3%，网络延迟从 8-10μs 降低到 2-3μs。这意味着CPU 可以释放出来处理更多的推理请求，等效于提升 10-15% 的推理吞吐量GPUDirect RDMA：GPU 显存与网卡直接通信，绕过 CPU 内存，减少一次数据拷贝（从 GPU显存到 CPU 内存再到网卡），端到端延迟降低 30-40%。

在多卡推理场景中（如 70B 模型需要 4-8卡），卡间通信延迟的降低直接转化为推理速度的提升流量调度：智能网卡内置的流量调度器可以实现 ECMP 负载均衡和基于信用的拥塞控制（DCQCN），避免网络热点导致的推理延迟抖动。实测数据显示，在 500节点推理集群中，智能网卡将 P99 延迟从 500ms 降低到 300ms，延迟标准差从 150ms 降低到 50ms智能网卡的部署成本约为每张 2,000-3,000 美元（含硬件和软件授权），在一个 500节点的推理集群中，智能网卡总投入约 100-150 万美元，但带来的收益显著：P99 延迟降低40%，同时释放约 1,000 个 CPU 核心（相当于节省 50-100 台服务器的 CPU 成本，约 200-500万美元）。

ROI 周期约 3-6 个月。

### 10.2.3 转码 + AI 融合算力

腾讯独有的一个优势是其庞大的视频业务（腾讯视频、微信视频号、腾讯会议）积累了大量 GPU转码资源。这些资源在大模型时代被创造性地复用为 AI 算力，形成了腾讯独有的"转码 + AI融合算力"模式。（1）转码与推理的时域互补视频转码的负载高峰通常在晚间 20:00-24:00（用户观看高峰），而 AI 推理的负载高峰通常在白天09:00-18:00（企业客户使用高峰）。腾讯通过弹性调度系统，在白天将闲置的转码 GPU 用于 AI推理，晚间则回收用于转码。这种"分时复用"策略使得 GPU 利用率从单业务的 40-50% 提升到综合的70-80%。

具体数据：白天（09:00-18:00）AI 推理使用约 1,500 张转码 GPU，转码业务仅使用约 500张；晚间（20:00-24:00）转码业务使用约 1,800 张 GPU，AI 推理仅使用约 200张。通过分时复用，腾讯等效于拥有了 2,000 张额外的推理 GPU，而无需额外采购。（2）硬件层面的兼容性视频转码常用的 T4 GPU 与 AI 推理的硬件需求高度重合：T4 的 INT8 算力 130 TOPS，适合 AI推理的量化计算；T4 的 16GB 显存可以容纳 7B-13B 参数量的量化模型（如混元-Lite 7B INT4 仅需 4GB显存）；

T4 的视频编解码引擎（NVENC/NVDEC）与 AI 计算核心（TensorCore）可以并行工作，互不干扰。腾讯甚至开发了"转码 +AI"融合任务：在视频转码的同时，利用空闲的 Tensor Core 执行视频内容理解（如目标检测、场景识别、字幕生成），实现"一份算力、两份产出"。实测数据显示，T4 在执行 4K H.265转码的同时，可以额外执行 2-3 路视频的目标检测任务，GPU 整体利用率从 60% 提升到 90%。（3）具体成本数据通过转码 + AI 融合算力，腾讯每年节省的 GPU 采购成本约为：复用转码 GPU 约 2,000张（T4），等效于节省采购成本 2,000 × 5,000 美元 = 1,000 万美元；

分时复用提升利用率 20-30个百分点，等效于节省 500-800 张新增 GPU 的采购，约 250-400万美元；融合任务提升产出，等效于节省 300-500 张 GPU，约 150-250 万美元。综合每年节省约1,500-2,000 万美元的硬件投入，折合人民币约 1-1.4 亿元。

### 10.3.1 以软件优化替代硬件堆叠

腾讯 AI Infra 最核心的技术哲学是"用软件换硬件"——通过极致的软件优化，在较低的硬件配置上实现接近甚至超越竞品的性能。这一理念贯穿训练和推理的全生命周期，是腾讯"低成本"策略的技术根基。（1）训练侧的软件优化腾讯 Angel 训练框架的核心优化技术栈包括以下几个关键技术：3D 并行 + ZeRO 优化：结合模型并行、数据并行、流水线并行，并引入 ZeRO（ZeroRedundancy Optimizer）技术消除冗余的显存占用。在 2,048 卡训练 500B MoE 模型时，每张 GPU的显存占用控制在 65GB（H800 为 80GB），剩余 15GB 用于激活值和临时变量，避免了 ZeRO-3带来的额外通信开销。

ZeRO 分为三个阶段：ZeRO-1 仅分割优化器状态，显存节省约 4倍；ZeRO-2 分割优化器状态 + 梯度，显存节省约 8 倍；ZeRO-3 分割优化器状态 + 梯度 +参数，显存节省约 16 倍，但通信开销增加 50%。腾讯选择ZeRO-2，在显存节省和通信开销之间取得平衡选择性重计算（SelectiveRecomputation）：不是所有的前向计算都需要保存用于反向传播。Angel框架通过自动分析，仅对显存占用大但计算量小的操作（如 LayerNorm、Softmax、Dropout）做重计算，对计算密集型操作（如矩阵乘法、卷积）保留激活值。

相比全量重计算（GradientCheckpointing），训练速度仅慢 5-8%，但显存节省 40-50%。相比不重计算，显存节省40-50%，训练速度仅慢 5-8%通信计算重叠：通过将 All-Reduce 通信与反向传播计算重叠，隐藏 60-70% 的通信延迟。具体实现是将梯度按层分组，每层的梯度计算完成后立即发起通信，同时开始下一层的计算。在 2,048卡集群上，通信开销占比从 25-30% 降低到 10-15%混合精度训练：FP16 计算 + FP32主权重的混合精度策略，在保持训练精度的同时将显存占用降低 40-50%，计算速度提升 1.5-2倍（利用 Tensor Core 的 FP16 加速）。

同时引入 Loss Scaling 技术防止 FP16 下的梯度下溢综合效果：通过上述软件优化，腾讯在 2,048 卡 H800 集群上训练 500B MoE模型的实测性能：MFU（Model FLOPs Utilization）达到 52-55%（行业平均水平 40-45%，字节约40-45%，阿里约 45-50%）；线性加速比 0.85（从 256 卡扩展到 2,048 卡，行业平均 0.70-0.75）；每Token 训练成本约 0.0003 元（按 2,048 卡 H800 每小时租赁成本 2,000 元、训练速度 50,000 tokens/s计算）；

训练 1T Token 数据总耗时约 23 天（行业同等规模通常需要 30-40 天，按 MFU 40-45%计算）。（2）推理侧的软件优化推理侧的软件优化更加精细，腾讯的技术栈包括：动态批处理（DynamicBatching）：不同于传统的静态批处理（等待固定数量的请求或超时后组批），腾讯的 ContinuousBatching 实现请求级别的动态调度——每个 Decode步骤结束后，检查是否有请求完成，如有则立即释放其占用的显存并插入新请求。这使得 GPU利用率从静态批处理的 50-60% 提升到 85-90%，吞吐量提升 2-3 倍Prefix Caching：对于共享系统提示词（System Prompt）的请求，其 KV Cache可以跨请求复用。

在典型的客服场景中，系统提示词约 1,000 Token，Prefix Caching 可以节省30-40% 的 KV Cache 显存，等效于支持多 30-40% 的并发请求投机采样（Speculative Decoding）：使用一个 7B 的小模型作为"草稿模型"快速生成候选 Token序列（每次生成 5-8 个 Token），再用 70B的大模型并行验证。由于大模型验证是并行的（一次验证多个Token），而小模型生成是串行的，综合速度可以提升 1.5-2 倍。腾讯在混元-Turbo上实测，投机采样的接受率约为 70-80%（即 80% 的草稿 Token 被大模型接受），生成速度从2,800 tokens/s 提升到 4,500 tokens/s模型蒸馏：将混元-Max（500B MoE）的知识蒸馏到混元-Turbo（70B Dense），在保持 90-95%效果的同时，推理成本降低 80%。

蒸馏的具体策略包括：Logit 蒸馏（对齐输出概率分布，权重0.5）、Feature 蒸馏（对齐中间层特征，权重 0.3）、Attention 蒸馏（对齐注意力模式，权重0.2）。蒸馏训练数据约 100B Token，训练耗时约 7 天（256 卡 H800）

### 10.3.2 集群稳定优先策略

腾讯 AI Infra 的另一个显著特点是极度重视稳定性。这与其服务的企业客户和政务客户对 SLA 的高要求直接相关。对于金融客户，系统不可用可能导致每分钟数百万元的损失；对于政务客户，系统不可用可能影响公共服务的正常运行。因此，腾讯将稳定性作为 AI Infra设计的第一优先级，甚至高于性能和成本。（1）故障预测与预防腾讯建立了完善的 GPU 集群故障预测系统，覆盖硬件、网络、软件三个层面：XID 错误监控：实时监控每张 GPU 的 XID 错误计数（NVIDIA GPU 的错误报告机制），当XID 错误频率超过阈值（如每小时 > 3 次）时，自动将该节点标记为"亚健康"并迁移任务。

XID错误类型包括：XID 13（GPU 图形引擎异常）、XID 31（GPU 内存错误）、XID 43（GPU掉电）等。通过历史数据分析，腾讯发现 XID 错误频率与后续硬件故障有强相关性——XID错误频率 > 3 次/小时的节点，在 48 小时内发生硬件故障的概率超过 60%温度预警：GPU 温度超过 85°C 时触发预警（检查散热系统），超过 90°C时自动降频（性能降低 20-30%），超过 95°C时自动下线（保护硬件）。数据中心环境温度通常控制在 22-25°C，GPU 满载温度通常在75-85°C内存 ECC 错误：监控 GPU 显存的 ECC 错误计数，当不可纠正错误（UE）发生时立即下线（数据已损坏），当可纠正错误（CE）频率超过阈值（如每天 > 10次）时预防性更换（硬件即将故障）网络丢包检测：通过 RDMA 网络的丢包率监控，当丢包率超过 0.01%时触发告警（检查光模块和光纤），超过 0.1%时自动切换链路（备用链路）。

正常状态下丢包率应 < 0.001%（2）故障快速恢复即使做了充分的预防，大规模集群的故障仍然不可避免。腾讯的故障恢复策略分为训练和推理两个场景：训练任务：通过异步 Checkpoint + 弹性训练框架，单节点故障后的恢复时间控制在 5分钟以内（行业平均 15-30 分钟）。具体流程：检测到故障（10 秒）→ 从最近的 Checkpoint恢复（2-3 分钟，增量 Checkpoint 约 200-500GB）→ 将故障节点的任务重新分配到其他节点（1-2分钟）→ 继续训练。故障恢复后训练速度不降低（因为 Checkpoint是异步的，恢复后从断点继续）推理服务：通过多副本 +自动扩缩容，单节点故障对服务的影响控制在秒级。

具体实现：每个推理服务至少部署 3个副本（分布在不同节点），负载均衡器每 5 秒检测一次副本健康状态，故障副本的流量在 3秒内切换到健康副本。用户感知到的影响仅为 3-5 秒的延迟增加，不会收到错误响应（3）SLA 保障腾讯 AI 推理服务的 SLA 承诺及实际运行数据：可用性：承诺 99.95%（月度不可用时间不超过 21.6 分钟），实际 2024 年全年平均 99.97%首 Token 延迟 P99：承诺不超过 500ms，实际 380ms端到端延迟 P99（500 Token 输出）：承诺不超过 5 秒，实际 3.2 秒吞吐量保障：承诺不低于承诺值的 90%，实际 95%+

### 10.9.1 Angel 训练框架技术细节

腾讯自研的 Angel 训练框架是其"软件优化优先"策略的核心体现。以下从架构设计、关键优化、性能表现三个维度详细解析。（1）架构设计Angel 框架采用分层架构设计，包括以下几个核心组件：调度层：负责任务调度、资源分配、故障恢复。调度器根据集群实时负载动态调整任务分配，避免"木桶效应"（最慢的节点决定整体速度）通信层：负责分布式通信（All-Reduce、All-to-All、Broadcast）。通信层支持多种通信后端（NCCL、Gloo、MPI），并根据网络拓扑自动选择最优通信策略计算层：负责模型计算、梯度计算、优化器更新。

计算层支持多种并行策略（数据并行、模型并行、流水线并行），并自动选择最优的并行配置存储层：负责数据加载、Checkpoint 保存、日志记录。存储层采用异步I/O，避免阻塞训练过程（2）关键优化技术3D 并行 +ZeRO-2：结合数据并行（DP=16）、张量并行（TP=8）、流水线并行（PP=16），并引入 ZeRO-2优化（分割优化器状态 + 梯度，显存节省约 8 倍）。在 2,048 卡训练 500B MoE 模型时，每张 GPU的显存占用控制在 65GB（H800 为 80GB），剩余 15GB 用于激活值和临时变量选择性重计算：仅对显存占用大但计算量小的操作（如 LayerNorm、Softmax、Dropout）做重计算，对计算密集型操作（如矩阵乘法）保留激活值。

相比全量重计算，训练速度仅慢5-8%，但显存节省 40-50%通信计算重叠：通过将 All-Reduce 通信与反向传播计算重叠，隐藏 60-70% 的通信延迟。具体实现是将梯度按层分组，每层的梯度计算完成后立即发起通信，同时开始下一层的计算梯度压缩：采用 Top-K 稀疏化策略，仅传输梯度中绝对值最大的 25%的参数，其余参数置零。通信数据量压缩到原始大小的 1/4，训练速度仅慢3-5%，但网络带宽需求降低 70%（3）性能表现Angel 框架在腾讯混元大模型训练中的实测性能：MFU（Model FLOPs Utilization）：52-55%（行业平均 40-45%，字节约 40-45%，阿里约45-50%）线性加速比：0.85（从 256 卡扩展到 2,048 卡，行业平均 0.70-0.75）每 Token 训练成本：约 0.0003 元（按 2,048 卡 H800 每小时租赁成本 2,000 元、训练速度 50,000tokens/s 计算）训练 1T Token 数据总耗时：约 23 天（行业同等规模通常需要 30-40 天，按 MFU 40-45% 计算）

### 10.9.2 BladeLLM 推理引擎技术细节

腾讯自研的 BladeLLM 推理引擎是其"低成本"策略的核心体现。以下从架构设计、关键优化、性能表现三个维度详细解析。（1）架构设计BladeLLM 采用模块化架构设计，包括以下几个核心组件：请求调度器：负责请求接收、排队、调度。调度器采用 Continuous Batching策略，实现请求级别的动态调度显存管理器：负责 KV Cache 的分配、回收、Offload。显存管理器采用 PagedAttention 技术，将KV Cache 按页管理（每页 16 Token）计算引擎：负责模型推理计算。计算引擎集成了 FlashAttention、Flash-Decoding 等优化技术量化引擎：负责模型量化（INT8/INT4）。

量化引擎支持多种量化策略（PTQ、QAT、AWQ），并根据 GPU 负载动态调整量化精度（2）关键优化技术PagedAttention：将 KV Cache 按页管理（每页 16 Token，约128KB），避免显存碎片。显存利用率从 30-50% 提升到 90%+Continuous Batching：动态组批，请求完成即释放、新请求即插入。吞吐量提升 2-3 倍（相比Static Batching）Speculative Decoding：用 7B 小模型草稿加速 70B 大模型生成。生成速度提升 1.5-2 倍，精度无损KV Cache Offload：将部分 KV Cache 卸载到 CPU 内存，按需加载回 GPU。

GPU 显存节省30-40%，支持更多并发Prefix Caching：共享前缀的 KV Cache 跨请求复用。KV Cache 显存节省 30-40%（3）性能表现BladeLLM 在混元-Turbo（70B Dense 模型）上的实测性能：单机 8 卡 A10（24GB 显存，INT8 量化）：吞吐量 1,200 tokens/s，首 Token 延迟 180ms，500Token 端到端延迟 3.5s单机 8 卡 A100（80GB 显存，FP16）：吞吐量 2,800 tokens/s，首 Token 延迟 95ms，500 Token端到端延迟 1.8s4 卡 A100（80GB 显存，FP16）：吞吐量 1,500 tokens/s，首 Token 延迟 120ms，500 Token端到端延迟 2.5s（性价比最优配置）单机 8 卡 A100（80GB 显存，INT8 量化）：吞吐量 4,200 tokens/s，首 Token 延迟 75ms，500Token 端到端延迟 1.2s（性能最优配置）

腾讯不是简单的"卖算力"，而是提供"算力 + 算法 +行业经验"的打包方案，帮助产业客户快速落地 AI 应用。（2）私有化部署能力腾讯的私有化部署能力在国内互联网厂商中最强，体现在：门槛低：50 万元起步（单机 2-8 卡），远低于字节的 200 万元和阿里的 150 万元方案成熟：提供轻量版（50-200 万元）、标准版（200-800 万元）、企业版（800-3,000万元）三种标准化方案，交付周期 4-32 周国产化适配：支持燧原 GPU + 麒麟 OS + 达梦数据库 + 东方通中间件，100%国产化，满足信创要求安全合规：通过等保三级、密评三级等认证，支持完全私有化部署，数据不出企业防火墙（3）成本优势腾讯的成本优势体现在多个层面：推理成本最低：0.008 元/千 Token（混元-Turbo），低于字节的 0.012 元和阿里的 0.010 元私有化部署成本最低：三年 TCO 约 200-500 万元（轻量版），低于字节的 500-1,000万元和阿里的 400-800 万元存量复用节省成本：通过转码 + AI 融合算力、分时复用等策略，每年节省约 2,000万美元的硬件成本软件优化降低硬件依赖：通过 Angel、BladeLLM 等软件优化，MFU 达到 52-55%（行业平均40-45%），等效于节省 20-30% 的 GPU（4）政务项目经验腾讯在政务领域的经验最丰富，数字广东项目覆盖 10+ 个省份，服务超过 5亿用户。

政务项目的成功关键在于：长期投入：数字广东成立于 2017 年，至今已运营 8 年，积累了丰富的政务项目经验本地化服务：在每个省份设立本地化团队（含驻场运维人员），提供 7×24 小时技术支持持续优化：根据政务客户的反馈持续优化产品（每季度更新一次），满足政务场景的特殊需求

### 10.9.2 面临的挑战

（1）GPU 规模限制腾讯的 GPU 总量（6,000-8,000 张）远低于字节（30,000+ 张）和阿里（15,000+张），这带来以下挑战：训练能力受限：无法训练超大规模模型（如 GPT-4 级别的万亿参数模型），混元-Max 仅约500B 参数并发能力受限：无法支撑超大规模 C 端流量（如抖音级别的日均数十亿次 API 调用）多模态能力受限：多模态模型（视频理解、图像生成）需要大量 GPU训练，腾讯的多模态能力弱于字节（2）C 端场景经验不足腾讯主要服务 B 端（产业客户）和 G 端（政务客户），在 C端场景（社交、娱乐、内容）的经验相对不足。

这导致：内容生成能力弱：在短视频生成、图像生成、音乐生成等内容生成场景，腾讯的能力弱于字节高并发经验不足：C 端场景需要支撑超高并发（如双11、春晚红包），腾讯在这方面的经验不如字节和阿里用户增长经验不足：C 端产品需要快速迭代、用户增长，腾讯的"克制型"策略与 C端的"快速试错"文化不匹配（3）品牌认知度在 AI 大模型领域，腾讯混元的品牌认知度弱于字节豆包和阿里通义千问。根据 2024年的市场调研：品牌认知度：豆包 85%、通义千问 78%、混元 65%、DeepSeek 90%（开源社区）市场份额：豆包 35%、通义千问 28%、混元 18%、DeepSeek 12%、其他 7%品牌认知度的差距可能影响腾讯在 AI 市场的竞争力，特别是在 C 端和中小企业市场。

### 10.9.3 未来战略方向

腾讯 AI Infra 的未来战略方向可以概括为"三个聚焦"：聚焦产业 AI：继续深耕金融、医疗、政务等传统产业，将产业 Know-how做深做透，形成不可替代的竞争壁垒。目标：2026 年产业客户数量突破 1,000 家，覆盖 30+个行业聚焦私有化部署：继续降低私有化部署门槛（目标 2026 年降低到 30万元），提升私有化部署的自动化程度（目标交付周期缩短 50%）。目标：2026年私有化部署客户数量突破 500 家聚焦成本优化：继续通过软件优化和存量复用降低成本（目标 2026 年推理成本降低到 0.005元/千 Token），提升单位算力的成本效率。

目标：2026 年 MFU 提升到 60%+本章核心要点：腾讯 AI Infra的核心竞争力不在于算力规模，而在于"克制型算力策略"——通过软件优化（占投入60%+）、存量复用（年省 1,500-2,000 万美元）、投资绑定（年省 3,000-5,000万美元）等手段，在较低的硬件投入下实现高质量的 AI能力输出。这种策略使其在产业落地（金融、医疗、政务）、私有化部署（50 万元起步）、中型企业服务等领域具有独特优势，是"稳重低成本"的典型代表。腾讯的核心数据：GPU 总量 6,000-8,000张，最大集群 2,048 卡，MFU 52-55%，推理成本 0.008 元/千 Token，SLA 99.97%。

面临的挑战包括GPU 规模限制、C 端场景经验不足、品牌认知度较弱（65%）。未来战略聚焦产业AI、私有化部署、成本优化三个方向。
