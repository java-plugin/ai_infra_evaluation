## 3.1.1 Prefill 阶段详解

大模型推理的第一个阶段是 Prefill（预填充），也称为 PromptProcessing。在这个阶段，模型处理用户输入的整个 prompt（包括 system prompt、历史对话、RAG检索结果和当前问题），计算所有输入 token 的 KV Cache。Prefill 的计算特征：Prefill 是一个 compute-bound 的过程。输入 prompt 的所有 token可以并行处理（不像 Decode 阶段需要逐 token 生成），本质上是一次或多次大矩阵乘法。计算量 = 2 ×参数量 × 输入 token 数（FLOPs）。

例如，一个 70B 模型处理 2000 tokens 的 prompt，计算量 = 2 × 70× 10 × 2000 = 2.8 × 10 FLOPs。在 H100 上（BF16 算力 989 TFLOPS），理论计算时间 = 2.8 ×10 / 9.89 × 10 ≈ 2.83 秒。实际时间通常更长（因为内存访问、通信等开销），约 1-5秒（取决于 prompt 长度和 GPU 配置）。Prefill 的显存需求：Prefill 阶段需要为每个输入 token 计算并存储 KV Cache。KV Cache 大小 = 2 ×层数 × KV 头数 × 头维度 × 输入 token 数 × 精度字节数。

以 LLaMA-2 70B 为例（80 层、8 个 KV头、头维度 128、BF16 精度）：每个 token 的 KV Cache = 2 × 80 × 8 × 128 × 2 bytes = 327,680 bytes ≈320KB。2000 tokens 的 KV Cache ≈ 640MB。如果 batch size = 16，总 KV Cache ≈ 10.24GB。Prefill 的优化方向：Chunked Prefill（将长 prompt 分成多个 chunk 处理，避免单次 Prefill 占用过多GPU 时间导致 Decode 请求饥饿）、Flash Attention（减少 Prefill 阶段 Attention计算的显存占用和计算量）、多卡 TP（将 Prefill 计算分布到多张 GPU 上，降低单卡计算压力）。

## 3.1.2 Decode 阶段详解

Decode 阶段是逐 token 生成的过程。每生成一个 token，模型需要：（1）将上一个 token 的embedding 输入模型，经过所有 Transformer 层计算；（2）计算当前 token 与所有之前 token 的Attention（使用 KV Cache 避免重复计算）；（3）通过 LM Head 得到下一个 token的概率分布；（4）采样得到下一个 token。Decode 的计算特征：Decode 是一个 memory-bound 的过程。每生成一个token，需要从显存中读取全部模型权重（70B 模型约140GB），但实际计算量很小（仅一次矩阵向量乘法，而非矩阵乘法）。

以 H100 为例：生成一个 token的理论时间 = 模型大小 / 显存带宽 = 140GB / 3350GB/s ≈ 42ms。实际时间约50-80ms（因为除了权重读取，还有 KV Cache 读取、采样等开销）。这意味着 H100 上 70B模型的理论生成速度约 12-20 tokens/s。Decode 阶段的 batch 效应：与 Prefill 不同，Decode 阶段可以通过 batching 多个请求来提高 GPU利用率。当 batch size = 1 时，GPU 的内存带宽利用率很低（因为矩阵向量乘法无法充分利用 TensorCore）。

当 batch size 增加到 8-16 时，多个请求的向量可以拼接成矩阵，充分利用 Tensor Core的矩阵乘法能力，吞吐量可以提升 4-8 倍。但 batch size 过大会导致 KV Cache 显存不足。最优 batch size取决于模型大小、显存容量和 KV Cache 大小。

## 3.1.4 推理性能指标体系

指标之间的关系：TTFT 主要受 Prefill 计算时间和排队延迟影响；TPOT 主要受 Decode阶段的显存带宽和 batch size 影响；吞吐量 = GPU 数量 × 单 GPU吞吐量，但受流量调度效率影响。在实际优化中，TTFT 和吞吐量往往存在矛盾——为了降低TTFT，需要减少排队（即预留更多 GPU 资源），但这会降低整体吞吐量利用率。

## 3.2.1 为什么需要 PD 分离

在传统的推理部署方式中，Prefill 和 Decode 在同一组 GPU上混合执行。这种方式存在严重的资源争抢问题：问题一：Prefill 阻塞 Decode。当一个长 prompt 的 Prefill 请求到达时（如 32K tokens），Prefill计算可能持续 5-10 秒。在此期间，同一 GPU 上的 Decode 请求被阻塞（因为 GPU 的计算资源被 Prefill占用），导致正在生成的用户的 TPOT 从 50ms 飙升到 500ms 甚至更长，用户体验严重下降。问题二：资源利用率不均衡。Prefill 是 compute-bound的，需要高算力但显存占用相对较少（主要是输入 KV Cache）；

Decode 是 memory-bound的，需要高显存带宽和大显存（存放模型权重 + 所有并发请求的 KV Cache）。混合部署时，GPU的算力和显存无法同时被充分利用——Prefill 时算力满载但显存空闲，Decode 时显存满载但算力空闲。问题三：调度灵活性差。混合部署无法针对 Prefill 和 Decode的不同特征进行独立优化和扩缩容。例如，在白天高峰期可能需要更多 Decode 资源（高并发），而Prefill 需求相对稳定。

## 3.2.2 Prefill 节点设计

Prefill 节点专门负责处理 prompt 的预填充计算。设计要点：硬件选型：优先选择高算力的 GPU（如 H100 SXM 或 B200），因为 Prefill 是 compute-bound的。显存容量需求相对较低（主要是输入 KV Cache，通常 < 10GB perrequest），因此不需要最大显存的 GPU。GPU 数量通常较少（如 4-16 张），因为 Prefill的计算量虽然大，但持续时间短（每个请求 1-5 秒），GPU 利用率容易达到 80%+。软件优化：启用 Flash Attention（减少 Prefill 的 Attention 计算显存和延迟）、启用 ChunkedPrefill（将长 prompt 分成多个 chunk，每个 chunk 处理 512-2048 tokens，避免单个 Prefill 占用 GPU过久）、使用 TP=2 或 TP=4（将 Prefill 计算分布到多张 GPU 上，降低单 Prefill 延迟）。

容量规划：Prefill 节点的容量取决于日均请求量和平均 prompt 长度。假设日均 100 万请求，平均prompt 2000 tokens，每次 Prefill 耗时 1 秒（H100 70B TP=2），则需要的 Prefill GPU 对数 = 100 万 / 86400× 1 ≈ 12 对（考虑峰值是平均的 3 倍，需要 36 对 = 72 张 H100）。

## 3.2.3 Decode 节点设计

Decode 节点专门负责逐 token 生成。设计要点：硬件选型：优先选择高显存带宽和大显存的 GPU（如 H200 141GB 或 B200 192GB），因为 Decode是 memory-bound 的，且需要为大 batch size 预留 KV Cache 空间。GPU 数量通常较多（如 16-64张），因为每个 Decode 请求需要持续占用 GPU 直到生成完成（通常 10-60 秒）。关键参数：最大并发 batch size（受 KV Cache 显存限制）、TPOT 目标（通常 < 50ms）、单 GPU吞吐量（tokens/s）。

KV Cache 显存计算：以 70B 模型为例，每个 token 的 KV Cache 约 320KB。如果最大 batch size =32，最大序列长度 = 8192 tokens，则 KV Cache 总显存 = 32 × 8192 × 320KB ≈80GB。加上模型权重（140GB，TP=2 时每卡 70GB），总显存需求约 150GB——需要 H200（141GB）或TP=2 的 H100（2 × 80GB = 160GB）。

## 3.2.4 KV Cache 传输机制

PD 分离的核心技术挑战是 KV Cache 从 Prefill 节点到 Decode 节点的高效传输。传输数据量：每个请求的 KV Cache 大小 = 2 × 层数 × KV 头数 × 头维度 × 序列长度 ×精度字节数。以 70B 模型、2000 tokens 输入为例，KV Cache 约 640MB。传输 640MB 数据：传输优化：GPU Direct RDMA：KV Cache 直接从 Prefill GPU 的显存通过 RDMA 传输到 Decode GPU的显存，绕过主机内存。延迟最低，但需要 Prefill 和 Decode 节点都有 RDMA 网卡。

异步传输 + 流水线：Prefill 计算完第 i 层的 KV Cache 后立即开始传输，同时继续计算第 i+1层。这样传输和计算可以重叠，总延迟 ≈ max(计算时间, 传输时间) 而非两者之和。KV Cache 压缩：在传输前对 KV Cache 进行量化压缩（如 FP16 →INT8），数据量减半，传输时间减半。但会引入一定的精度损失。预取策略：根据请求调度信息，提前在 Decode 节点预留显存空间，避免 KV Cache到达时因显存不足而等待。

## 3.2.5 流量调度与负载均衡

PD 分离架构需要一个智能的流量调度器（Dispatcher），负责将请求路由到合适的 Prefill节点，并将完成 Prefill 的请求路由到合适的 Decode 节点。调度策略：Prefill 调度：基于 Prefill 节点的当前负载（排队请求数、GPU利用率）进行负载均衡。优先选择负载最低的节点。对于长 prompt请求，可以专门调度到算力最强的节点。Decode 调度：基于 Decode 节点的可用 KV Cache 显存和当前 batch size进行调度。优先选择有足够 KV Cache 空间且 batch size未满的节点。

考虑会话粘性——同一用户的后续请求（多轮对话）应该调度到同一个 Decode节点，以复用 KV Cache。弹性伸缩：根据实时流量动态调整 Prefill 和 Decode 节点的数量。白天高峰期增加 Decode节点，夜间低峰期减少总节点数以节省成本。

## 3.2.7 PD 分离的实际部署案例

以下是某头部 AI 公司实施 PD 分离架构的完整案例，供读者参考：背景：该公司运营一个日均处理 2000 万次对话的 AI 助手服务，使用 70B 模型部署在 256 张 H100上（32 台 8 卡服务器）。在混合部署模式下，高峰期 TTFT P99 经常超过 5 秒，用户投诉率上升。架构改造：将 256 张 H100 重新分配为：64 张用于 Prefill（8 台服务器），192 张用于 Decode（24台服务器）。Prefill 和 Decode 节点之间通过 InfiniBand NDR 400Gbps 网络连接。

使用自研的 KV Cache传输服务，基于 GPU Direct RDMA 实现显存到显存的直接传输。关键技术决策：（1）Prefill 使用 TP=4（每张 GPU 处理 1/4 的模型参数），将单次 Prefill 延迟从 4秒降低到 1.2 秒；（2）Decode 使用 TP=2（每对 GPU 处理一个完整的模型副本），最大化并发 batchsize（每对 GPU 支持 24-32 并发请求）；（3）KV Cache 传输使用异步流水线——Prefill 计算完第 i层后立即开始传输第 i 层 KV Cache，同时计算第 i+1层；

（4）调度器实现了会话粘性——多轮对话的后续请求优先调度到同一个 Decode节点，复用之前的 KV Cache。改造效果：TTFT P50 从 800ms 降低到 350ms（降低 56%），TTFT P99 从 5000ms 降低到900ms（降低 82%），TPOT P99 从 200ms 降低到 65ms（降低 67%），整体吞吐量从 800 tokens/s/GPU提升到 1150 tokens/s/GPU（提升 44%）。KV Cache 传输的平均延迟为 15ms（InfiniBandNDR），对用户体验几乎无感知。

经验教训：（1）Prefill 和 Decode 的比例不是一成不变的——需要根据实际的请求分布动态调整。该公司最终实现了弹性伸缩：白天高峰期 Prefill:Decode = 1:4，夜间低峰期调整为 1:2。（2）KV Cache传输的可靠性至关重要——一旦传输失败，整个请求需要重新Prefill。他们实现了传输重试机制和校验和验证，将传输失败率控制在 0.01%以下。（3）调度器的设计需要充分考虑边界情况——如 Decode 节点全部满载时的排队策略、Prefill完成但 Decode 节点不可用时的降级方案。

## 3.3.1 KV Cache 原理与显存占用计算

KV Cache 是 Transformer 推理优化的核心技术。在 Decode 阶段，每生成一个新 token都需要计算它与所有之前 token 的 Attention。如果不使用 KV Cache，每个新 token都需要重新计算所有之前 token 的 Key 和 Value 向量，计算量随序列长度线性增长。使用 KV Cache后，之前 token 的 K 和 V 向量被缓存，新 token 只需要计算自己的 K 和 V，然后与缓存中的所有 K、V做 Attention，将计算复杂度从 O(n) 降低到 O(n)。

KV Cache 显存占用公式：KV Cache 大小 = 2 × num_layers × num_kv_heads × head_dim × seq_len × dtype_bytes其中 ×2 是因为 Key 和 Value 各一份。注意：对于 GQA（Grouped Query Attention）模型（如LLaMA-2 70B），num_kv_heads 可能远小于 num_attention_heads（70B 的 num_attention_heads = 64，但num_kv_heads = 8），这大幅减少了 KV Cache 大小。

各模型的 KV Cache 占用对比（每 token，BF16 精度）：从表中可以看出，70B 级别模型在 128K 上下文下的 KV Cache 高达 40GB——这几乎等于一张 A10080GB 的全部显存。这就是为什么长上下文推理需要大显存 GPU（如 H200 141GB）或 KV Cache优化技术。

## 3.3.2 一级缓存：GPU HBM 上的 KV Cache

GPU HBM 是 KV Cache 的主要存储位置。所有正在活跃推理的请求的 KV Cache 必须驻留在 HBM上，因为 GPU 计算单元需要直接、高速地访问 KV Cache。HBM KV Cache 管理挑战：HBM 容量有限（A100 80GB、H100 80GB、H200141GB），需要同时容纳模型权重和所有活跃请求的 KV Cache。以 70B 模型（140GB 权重，TP=2时每卡 70GB）部署在 H100 80GB 上为例，每张卡剩余 10GB 用于 KV Cache，只能支持约 10GB / 320KB≈ 31,250 个 token 的 KV Cache——如果平均序列长度 4K tokens，只能支持约 8 个并发请求。

优化手段：PagedAttention（将 KV Cache 分成固定大小的page，按需分配和释放，避免内存碎片）、量化 KV Cache（FP16 →INT8，显存减半，精度损失通常可接受）、GQA/MQA（减少 KV 头数，从根本上减少 KV Cache大小）。

## 3.3.3 二级缓存：Host DRAM 上的 KV Cache

当 GPU HBM 的 KV Cache 空间不足时，可以将暂时不活跃的 KVCache（如用户暂停输入、等待工具返回结果的请求）offload 到主机内存（Host DRAM）。Host DRAM 的特征：容量大（通常 512GB-2TB，是 HBM 的 6-25 倍）、带宽低（DDR5-4800 约300-400 GB/s，是 HBM3 的 1/10）、延迟高（约 100ns，是 HBM 的 10 倍）。Offload/Reload 流程：（1）当新请求到达但 HBM KV Cache空间不足时，调度器选择最不活跃的请求（如最长时间没有新 token 到达的请求），将其 KV Cache 从HBM 复制到 Host DRAM；

（2）释放 HBM 空间给新请求；（3）当被 offload 的请求恢复活跃时，将其KV Cache 从 Host DRAM 复制回 HBM。性能影响：复制 1GB KV Cache 从 HBM 到 Host DRAM（通过 PCIe 5.0，有效带宽约 50GB/s）约需20ms。这个延迟对于用户暂停的场景是可接受的（用户暂停通常 > 1秒），但对于活跃请求会导致明显的卡顿。因此，offload 策略必须准确判断请求的活跃状态。

## 3.3.4 三级缓存：NVMe SSD 上的 KV Cache

对于更长期的 KV Cache 存储（如多轮对话中历史轮次的 KV Cache），可以将其持久化到 NVMeSSD 上。NVMe SSD 的特征：容量更大（单盘 3.84-15.36TB）、带宽中等（NVMe SSD 持续读取 5-7GB/s，随机读取 1-3 GB/s）、延迟较高（约 10-100μs）。应用场景：多轮对话的 KV Cache 复用——当用户发起新一轮对话时，历史轮次的 KV Cache可以从 SSD 快速加载回 HBM，避免重新计算。这对于客服、教育等长对话场景特别有价值。假设一个10 轮对话，每轮平均 2000 tokens，总 KV Cache 约 6.4GB（70B 模型）。

从 NVMe SSD 加载 6.4GB 约需1-2 秒，远快于重新 Prefill 计算（约 3-5 秒）。Prefix Caching 与 SSD：对于共享相同 system prompt或前缀的请求（如同一应用的数万用户），可以将前缀的 KV Cache 持久化到 SSD上，新请求到达时直接加载，避免重复计算。这在大规模服务中可以节省 30-50% 的 Prefill 计算量。

## 3.3.5 KV Cache 分层调度策略

三级 KV Cache 的分层调度需要解决以下问题：何时 offload：当 HBM KV Cache 使用率超过阈值（如 85%）时触发 offload。选择 offload目标的标准：LRU（Least Recently Used，最久未使用的请求优先）、LFU（Least FrequentlyUsed，使用频率最低的优先）、基于预测的智能调度（预测哪些请求短期内不会恢复活跃）。何时 reload：当被 offload 的请求恢复活跃（如用户发送了新消息、工具返回了结果）时，触发reload。如果 HBM 空间不足，需要先 offload 其他请求。

预取策略：对于可预测的访问模式（如多轮对话中用户通常在 30秒内发送下一条消息），可以提前将 KV Cache 从 DRAM/SSD 预取到 HBM，减少 reload 延迟。

## 3.3.6 PagedAttention 与 vLLM 实现

PagedAttention 是 vLLM 的核心创新，借鉴了操作系统虚拟内存的分页（Paging）思想来管理 KVCache。核心思想：将 KV Cache 分成固定大小的 block（通常 16 tokens 一个 block），每个 block可以存储在非连续的显存空间中。通过 block table（类似页表）记录每个序列的 block映射关系。这样解决了传统连续分配方式的内存碎片问题。内存碎片问题：在传统方式下，每个请求的 KV Cache 需要分配连续的显存空间。由于不同请求的序列长度不同，分配和释放后会产生大量碎片（类似内存碎片问题）。

例如，一个 1000 token的请求释放后留下 1000 token 的空洞，但一个 1500 token的新请求无法使用这个空洞，只能申请新的连续空间。在稳态下，内存碎片率可达 20-40%，意味着20-40% 的显存被浪费。PagedAttention 的收益：通过非连续分配，几乎消除了内存碎片（碎片率 < 5%），显存利用率从60-80% 提升到 95%+。这意味着同样的 GPU 可以支持更多的并发请求，吞吐量提升 20-50%。vLLM 的其他关键特性：Continuous Batching（动态batch，请求完成时立即移除、新请求立即加入，无需等待整个 batch 完成）、ParallelSampling（并行采样，一个 prompt 同时生成多个候选回答）、Beam Search（束搜索，在 beam 之间共享KV Cache 的公共前缀）。

## 3.3.7 Prefix Caching 与 RadixAttention

Prefix Caching：当多个请求共享相同的前缀（如 system prompt、few-shot examples）时，前缀的 KVCache 只需要计算一次，后续请求直接复用。这在以下场景中非常常见：所有用户共享相同的 system prompt（如"你是一个有帮助的助手..."）RAG 应用中所有请求共享相同的检索上下文Few-shot prompting 中所有请求共享相同的示例Prefix Caching 的节省量取决于前缀长度和请求数量。假设 system prompt 为 1000 tokens，日均 100万请求，每次 Prefill 计算 1000 tokens 约需 0.5 秒（H100 70B），则每天节省的 Prefill 计算时间 = 100 万 ×0.5 秒 = 50 万秒 ≈ 5.8 天的 GPU 时间。

Prefix Caching 可以将这部分计算完全消除。RadixAttention（SGLang）：RadixAttention 是 SGLang 框架提出的优化，使用 RadixTree（基数树/前缀树）来管理 KV Cache 的缓存和复用。Radix Tree 的每个节点代表一个 token序列片段，节点上存储该片段的 KV Cache。当新请求到达时，RadixAttention 在 Radix Tree中查找最长匹配的前缀，复用其 KV Cache，只需要计算剩余部分。RadixAttention 的优势在于：自动管理 KV Cache 的生命周期（通过引用计数，当没有请求引用某个节点时自动释放）、支持任意前缀的共享（不仅仅是严格的公共前缀，还包括部分重叠的前缀）、高效的内存管理（通过 Radix Tree 的合并和分裂操作，最大化 KV Cache 复用）。

## 3.3.8 KV Cache 优化的经济效益量化

KV Cache 优化技术的经济价值可以通过以下案例量化：案例：某 AI 服务商日均处理 500 万次 LLM 对话请求，使用 70B 模型部署在 64 张 H100上。平均输入长度 2000 tokens，平均输出长度 500 tokens。优化前（无 KV Cache 优化）：每张 H100 支持约 8 个并发请求（batch size = 8），64 张卡支持 512并发。日均 500 万请求 / 86400 秒 ≈ 58 请求/秒。每个请求平均占用 GPU 时间 = Prefill 2 秒 + Decode 500tokens × 50ms = 27 秒。

512 并发 × (86400 秒 / 27 秒/请求) ≈ 164 万次/天——远不够 500 万次。优化后（PagedAttention + Prefix Caching + KV Cache 量化）：PagedAttention 将显存利用率从 65%提升到 95%，等效 batch size 从 8 提升到 12（提升 50%）；Prefix Caching 复用率 40%（system prompt 约500 tokens，40% 的请求命中缓存），Prefill 时间减少 20%；KV Cache INT8 量化将每个请求的 KV Cache显存减半，等效 batch size 再翻倍到 24。

综合效果：64 张卡支持约 1536 并发，日均处理能力 = 1536 ×(86400 / 22) ≈ 605 万次/天——满足需求。经济价值：如果不做 KV Cache 优化，需要 64 × (500 / 164) ≈ 195 张 H100才能满足需求。优化后只需要 64 张，节省了 131 张 H100（约 131 × 25 万元 = 3275 万元）。KV Cache优化技术的投入（主要是工程开发成本，约 5-10 人 × 6 个月 = 300-600 万元）带来了超过 3000万元的硬件成本节省，ROI 超过 5 倍。

## 3.4.1 MoE 架构原理（以 Mixtral / Qwen2-MoE 为例）

MoE（Mixture of Experts）是一种稀疏激活的模型架构。与 Dense 模型（每个 token都经过所有参数）不同，MoE 模型将 FFN 层替换为多个"专家"（Expert），每个 token只被路由到其中少数几个专家（通常 1-2 个）进行处理。Mixtral 8×7B 架构详解：总参数量：46.7B（8 个专家各 7B + 路由层 + Attention 层）每个 token 激活的参数量：约 12.9B（2 个专家 × 7B + Attention 层）层数：32 层每层的专家数：8 个每个 token 选择的专家数：2 个（Top-2 routing）路由机制：一个可学习的 router（线性层 + softmax）为每个 token 计算对 8个专家的评分，选择评分最高的 2 个MoE 的核心优势：在相同的推理计算量下（激活参数量），可以拥有更大的总参数量（模型容量）。

Mixtral 8×7B 的推理计算量约等于一个 13B 的 Dense 模型，但效果接近 30B 级别的 Dense模型——因为 46.7B 的总参数量提供了更大的知识容量。MoE 的推理挑战：虽然每个 token 只激活 2 个专家，但所有 8个专家的权重都需要加载到显存中（因为不同 token 可能路由到不同专家）。因此 MoE模型的显存需求与同等总参数量的 Dense 模型相同（Mixtral 46.7B 需要约 93GB显存，FP16），但计算量只有 13B 级别。这使得 MoE 成为 memory-bound的架构——显存是主要瓶颈，算力反而有富余。

## 3.4.2 专家并行策略

MoE 模型的分布式推理需要专门的并行策略——专家并行（Expert Parallelism, EP）。专家并行的基本思想：将不同的专家分布到不同的 GPU 上。例如，8 个专家分布在 8 张 GPU上，每张 GPU 持有 1 个专家。每个 token 根据路由结果，通过 All-to-All 通信发送到对应专家所在的GPU 进行计算，计算完成后再通过 All-to-All 将结果发送回来。通信模式：MoE 层的通信模式是 All-to-All（每个 GPU 需要向其他所有 GPU发送数据）。All-to-All 的通信量 = 每个 GPU 发送的数据量 × (GPU 数 - 1)。

在 Top-2 routing 下，每个token 有 2/8 = 25% 的概率被路由到本 GPU 的专家，75% 的概率需要发送到其他 GPU。因此 All-to-All的数据量约为激活值的 75%。专家并行的优化：将专家并行与张量并行结合（TP + EP）：在同一台 8 卡服务器内，使用 TP 处理 Attention层，使用 EP 处理 MoE 层。这样 Attention 层使用 NVLink 的高带宽进行 AllReduce，MoE 层使用NVLink 进行 All-to-All。专家分组（Expert Grouping）：将多个专家放在同一张 GPU 上（如 8 个专家放在 4 张 GPU上，每卡 2 个专家），减少 All-to-All 的通信对端数量。

异步 All-to-All：使用 CUDA kernel 将 All-to-All 通信与计算重叠。

## 3.4.3 专家负载平衡

MoE 模型的一个关键挑战是专家间的负载不平衡。如果 router 将大部分 token路由到少数几个专家，这些专家所在的 GPU 会成为瓶颈，而其他 GPU 空闲等待。负载不平衡的度量：使用负载不均衡系数（Load Imbalance Factor）= max(各专家的 token 数) /avg(各专家的 token 数)。理想值为 1.0（完全均衡），实际值通常在 1.2-2.0 之间。解决方案：Auxiliary Loss（辅助损失）：在训练时加入一个辅助损失函数，惩罚负载不均衡的路由分布。这是最常用的方法，Mixtral 和 Qwen2-MoE 都使用了这种方式。

Expert Capacity：限制每个专家处理的 token 数量上限。超过容量的 token被"丢弃"（drop）或路由到备用专家。这种方法在推理时也可以使用，但可能导致精度下降。动态路由调整：在推理时根据各专家的实时负载动态调整路由阈值，将部分 token从过载专家转移到轻载专家。

## 3.4.4 专家 Offload 技术

由于 MoE 模型的所有专家都需要在显存中，但每个 token只激活少数专家，一个自然的优化思路是将不活跃的专家 offload 到主机内存或 SSD 上。Expert Offload 的基本原理：在推理时，根据当前 batch 中 token的路由结果，只将需要的专家加载到 GPU 显存中，不需要的专家保留在 Host DRAM 或 SSD 上。性能分析：以一个 8 专家模型为例，每个专家约 7B 参数（14GB FP16）。如果 batch 中的 token路由到了 3 个不同的专家，需要加载 3 × 14GB = 42GB 到 GPU。

如果这 3 个专家中有 2 个在 Host DRAM上，需要通过 PCIe 传输 28GB，耗时约 28GB / 50GB/s ≈ 560ms——这对于实时推理是不可接受的。实际可行的方案：Expert Offload 更适合 batch处理场景（如离线推理、训练），对于实时推理，更好的方案是：（1）使用足够大的 GPU 显存容纳所有专家；（2）使用量化（INT8/INT4）减少专家的显存占用；（3）使用预取策略，根据历史路由模式预测下一批需要的专家并提前加载。

## 3.4.5 MoE 通信模式与优化

MoE 的 All-to-All 通信是性能瓶颈之一。以下是优化策略：通信压缩：在 All-to-All 之前对激活值进行量化（FP16 → INT8），通信量减半。由于 MoE的激活值在专家间传输后还会经过 FFN计算，量化引入的误差会被后续计算"稀释"，对最终精度影响很小。通信-计算重叠：将 token按目标专家分组后，可以先发送第一组数据，同时开始准备第二组数据。或者在等待 All-to-All完成的同时，先开始处理已经到达的 token。Token 合并（Token Merging）：将路由到同一专家的多个 token 合并成一个 batch 进行计算，提高GPU 利用率。

这本质上是将多个小矩阵乘法合并成一个大矩阵乘法。

## 3.5.1 Continuous Batching 技术

传统的 static batching 方式：等待一个 batch 中的所有请求都生成完毕后，才开始处理下一个batch。问题：短请求生成完毕后，其 GPU 资源被浪费（等待长请求完成）。Continuous Batching（动态 batch / iteration-level scheduling）：在每一步 Decode迭代后，检查是否有请求已完成——如果有，立即将其移出 batch并释放资源；同时检查是否有等待中的新请求——如果有，立即加入 batch。这样 GPU资源始终被充分利用，不会因为长短请求混合而产生浪费。

性能收益：Continuous Batching 可以将吞吐量提升 2-4 倍（相对于 staticbatching），特别是在请求长度差异大的场景下（如混合了短问答和长文生成的请求）。实现要点：推理引擎需要在每一步 Decode迭代之间进行调度决策——这要求调度逻辑非常轻量（<1ms），不能成为瓶颈。vLLM、TensorRT-LLM、SGLang 都实现了 Continuous Batching。

## 3.5.2 Speculative Decoding 加速

Speculative Decoding（推测解码）是一种利用小模型（draft model）加速大模型（targetmodel）生成的技术。基本原理：（1）使用一个小模型（如 7B）快速生成 K 个候选 token（K 通常为4-8）；（2）使用大模型（如 70B）一次性验证这 K 个 token（大模型可以并行处理这 K 个 token 的Prefill）；（3）比较大模型和小模型对这 K 个 token的概率分布，接受一致的部分，从第一个不一致的位置重新生成。加速比分析：如果小模型的预测准确率约 80%，则 K=5 时平均可以接受 3.3 个 token（5 × 0.8^0 +... ≈ 3.3），即大模型每验证一次可以生成 3.3 个 token，加速比约 3.3 倍。

实际加速比通常在 1.5-2.5倍之间（取决于任务类型和小模型的质量）。适用场景：Speculative Decoding 最适合 Decode阶段是瓶颈的场景（memory-bound），因为它将多个 Decode 步骤合并为一次 Prefill步骤（compute-bound），利用了大模型在 Prefill 阶段更高的计算效率。

## 3.5.3 量化推理（INT8 / INT4 / FP8）

量化推理通过将模型权重从高精度（FP16/BF16）转换为低精度（INT8/INT4/FP8），减少显存占用和内存带宽需求，从而提升推理速度。量化方法对比：PTQ（Post-TrainingQuantization，训练后量化）：不需要重新训练，使用少量校准数据（128-1024 条样本）确定量化参数。代表方法：GPTQ（基于近似二阶信息的逐层量化）、AWQ（Activation-aware WeightQuantization，根据激活值的重要性保护关键权重）。PTQ速度快（几分钟到几小时），但精度损失略大。QAT（Quantization-Aware Training，量化感知训练）：在训练过程中模拟量化误差，让模型适应低精度。

精度损失最小，但需要重新训练（成本高）。量化对显存和吞吐量的实际影响（70B 模型，H100）：

## 3.5.4 模型蒸馏与剪枝

知识蒸馏（Knowledge Distillation）：使用大模型（teacher）的输出指导小模型（student）的训练，使小模型在保持较高速度的同时获得接近大模型的效果。例如，使用 70B 模型蒸馏出 7B 模型，7B模型的推理速度是 70B 的 10 倍，但效果可以达到 70B 的 85-95%（取决于蒸馏方法和任务类型）。模型剪枝（Pruning）：移除模型中不重要的参数（权重接近零的连接或整个注意力头）。结构化剪枝（移除整个头/层/专家）可以直接减少计算量；非结构化剪枝（移除单个权重）需要硬件支持稀疏计算才能加速。

目前大模型领域，剪枝的应用不如蒸馏广泛，因为大模型的参数冗余度较低（每个参数都承载了较多知识）。

## 3.6.1 混合精度训练（FP16 / BF16 / FP8）

混合精度训练是在训练过程中同时使用多种数值精度，在保证训练稳定性的前提下最大化计算效率。标准混合精度训练流程：（1）主权重（Master Weights）保持 FP32精度（用于参数更新）；（2）前向传播使用 BF16 或 FP16（利用 Tensor Core加速）；（3）反向传播使用 BF16 或 FP16；（4）梯度累积使用FP32（避免精度损失）；（5）参数更新使用 FP32（AdamW 优化器需要 FP32 的 momentum 和variance）。BF16 vs FP16：BF16 的动态范围与 FP32 相同（±3.4×10），因此不需要 lossscaling，训练更稳定。

FP16 的动态范围较小（±65504），需要 loss scaling防止梯度上溢。目前大模型训练几乎全部使用 BF16。FP8 训练：H100 首次支持 FP8 Tensor Core，理论上可以将训练速度翻倍。但 FP8的精度极低（E4M3 约 1.5 位有效数字），需要精细的 scaling 策略和特殊的训练技巧。目前 FP8训练仍处于实验阶段，仅部分模型（如 Nemotron）成功使用 FP8 训练。主要挑战：训练不稳定（lossspike）、需要逐层调优 scaling factor、并非所有算子都支持 FP8。

## 3.6.2 梯度累积与梯度检查点

梯度累积（Gradient Accumulation）：在显存不足时，通过多次前向/反向传播累积梯度，然后一次性更新参数。等效于增大 batchsize，但不增加显存占用。例如，batch_size=4、gradient_accumulation=8，等效 batch size =32，但显存占用仅相当于 batch_size=4。梯度检查点（Gradient Checkpointing / Activation Checkpointing）：在训练时不保存所有中间激活值（activation），而是在反向传播时重新计算。

这用计算时间换显存空间——显存占用减少约50-70%，但训练时间增加约 20-30%。对于 70B模型的全量微调，梯度检查点几乎是必须的（否则激活值的显存占用会超过 GPU 容量）。

## 3.6.3 ZeRO 优化器（ZeRO-1 / 2 / 3）

ZeRO（Zero Redundancy Optimizer）是 DeepSpeed的核心技术，通过将优化器状态、梯度和模型参数分片到多个 GPU上，消除数据并行中的冗余显存占用。ZeRO-3 的通信分析：在 ZeRO-3 中，每张 GPU 只持有模型参数的 1/N（N 为 GPU数量）。前向传播时，需要通过 AllGather 临时收集完整参数；反向传播时，同样需要AllGather。这意味着 ZeRO-3 的通信量是标准 DP 的 3 倍（前向 AllGather + 反向 AllGather + 梯度ReduceScatter）。

因此 ZeRO-3 需要高带宽的 GPU 互联（NVLink 或InfiniBand）才能避免通信成为瓶颈。

## 3.6.4 3D 并行策略（TP + PP + DP）

对于超大规模模型（100B+参数），单一的并行策略无法满足需求，需要组合使用多种并行方式——即 3D 并行。Tensor Parallelism（TP，张量并行）：将每一层的参数矩阵按列或行切分到多张 GPU上。优点：每层内部完全并行，延迟最低。缺点：每层都需要 AllReduce通信，通信频率高。适用：同一台服务器内的 GPU 之间（NVLink 高带宽）。推荐 TP度数：2-8（不超过一台服务器的 GPU 数量）。Pipeline Parallelism（PP，流水线并行）：将模型按层切分到不同 GPU 上。GPU 0 持有第 1-K层，GPU 1 持有第 K+1-2K层，以此类推。

优点：通信频率低（只在层间传递激活值）。缺点：存在"气泡"（bubble）——前面的GPU 计算时后面的 GPU 在等待。适用：跨服务器的 GPU 之间（InfiniBand带宽足够传递激活值）。推荐 PP 度数：2-16。Data Parallelism（DP，数据并行）：每张 GPU 持有完整的模型副本，处理不同的数据。梯度通过AllReduce 同步。适用：模型可以放入单卡显存时。与 ZeRO结合（ZeRO-DP），可以在模型无法放入单卡时也使用数据并行。3D 并行配置示例：训练 LLaMA-2 70B 在 128 张 A100（16 台 8 卡服务器）上：TP = 8（同一台服务器内 8 卡，NVLink 互联）PP = 4（4 台服务器组成一个流水线，InfiniBand 互联）DP = 4（4 组流水线并行处理不同数据）总计：8 × 4 × 4 = 128 张 GPU

## 3.6.5 Flash Attention 原理与性能

Flash Attention 是 Transformer Attention 计算的核心优化算法，由 Tri Dao 等人在 2022 年提出。标准 Attention 的问题：标准 Attention 需要将完整的 N×N Attention 矩阵（N为序列长度）写入显存再读回。对于长序列（如 32K tokens），Attention 矩阵大小为 32K × 32K × 2bytes（FP16）= 2GB——这远超 GPU 的 SRAM（L1/L2 缓存，约 20-50MB），导致频繁的 HBM读写，成为性能瓶颈。

Flash Attention的核心思想：使用分块计算（Tiling）和重计算（Recomputation）技术，避免将完整的 Attention矩阵写入 HBM。将 Q、K、V 分成多个 block（如 64×64），每个 block 在 SRAM 中完成 Attention计算，只将最终结果写回 HBM。这样 HBM 访问量从 O(N) 降低到O(N)，大幅减少了内存带宽需求。性能对比（A100，序列长度 4K，batch size 8）：Flash Attention 不仅加速了 Attention 计算，更重要的是将显存占用从 O(N) 降低到O(N)，使得训练长序列模型（32K、128K 上下文）成为可能。

## 3.6.6 训练 Pipeline 工程化最佳实践

一个生产级的大模型训练 Pipeline 不仅仅是训练脚本本身，还包括数据准备、训练监控、故障恢复、评估发布等多个环节。以下是经过实战验证的最佳实践：数据 Pipeline：（1）数据预处理集群：使用 Apache Spark 或 Ray 进行大规模数据清洗和tokenization。100B tokens 的数据预处理约需 500 CPU 核 × 4 小时。（2）数据版本管理：使用DVC（Data Version Control）或 LakeFS管理训练数据版本，确保每次训练的数据集可追溯。（3）数据质量监控：实时监控训练数据的 token分布、语言分布、重复率等指标，异常时自动告警。

（4）数据混配比（DataMixing）：不同领域数据的比例对模型效果影响巨大。推荐参考 LLaMA 的数据配比：英文网页25%、代码 20%、百科 15%、书籍 10%、学术论文 10%、其他 20%。训练监控体系：（1）训练 Loss 监控：实时监控 training loss 和 validation loss，设置 loss spike检测（loss 突然增加超过 30% 时告警）。（2）梯度范数监控：梯度范数突然增大通常预示训练不稳定，需要关注。（3）学习率曲线：确认学习率按预期 schedule 变化。

（4）GPU 状态监控：DCGM 采集GPU 利用率、温度、功耗、ECC 错误。（5）网络监控：InfiniBand端口错误计数、带宽利用率。（6）训练进度预估：基于当前 tokens/s 预估训练完成时间，偏差超过10% 时告警。故障自动恢复：（1）Checkpoint 策略：每 500 步保存一次常规checkpoint（异步写入，不阻塞训练），每 2000 步保存一次完整checkpoint（含优化器状态）。（2）故障检测：使用 watchdog进程监控训练进程状态，训练进程挂起超过 5 分钟自动触发恢复。（3）自动恢复流程：检测到故障 →隔离故障节点 → 从备用节点池分配替代节点 → 从最近的 checkpoint 恢复训练 → 验证恢复后 loss正常。

整个恢复过程目标 < 15 分钟。（4）训练日志持久化：将训练日志实时写入远程存储（如S3），避免节点故障导致日志丢失。评估 Pipeline：（1）自动评估：每 1000 步自动在预设的 eval set 上评估模型效果。Eval set 应覆盖多个维度：通用知识（MMLU）、数学推理（GSM8K/MATH）、代码生成（HumanEval/MBPP）、中文理解（C-Eval）。（2）人工评估：每 10000 步进行一次人工抽样评估（100-200条样本），评估维度包括：事实准确性、逻辑连贯性、安全性、指令遵循度。

（3）回归检测：新checkpoint 的效果不应低于前一个 checkpoint（除非在预期的训练波动范围内）。如果连续 3次评估效果下降，自动暂停训练并告警。

## 3.7 避坑指南：推理/训练优化常见误区

误区一：盲目追求最大 batch size，忽视 TTFT典型表现：为了最大化吞吐量，将 batch size 设置得很大（如 64 或128），导致新请求需要等待很长时间才能被加入 batch，TTFT 飙升到 5-10 秒。反例：某企业部署了一个 70B 推理服务，为了追求高吞吐量将 max_batch_size 设为64。在测试中吞吐量达到了 2000 tokens/s，但 TTFT P99 达到了 8 秒——因为新请求需要等待 batch 中至少一个请求完成才能被加入。在实际使用中，用户反馈"响应太慢"，即使生成速度本身并不慢。

正确做法：batch size 的设置需要在吞吐量和 TTFT 之间平衡。推荐策略：设置 max_batch_size 的同时设置max_wait_time（新请求最多等待 200-500ms 就必须被加入 batch）。使用 Continuous Batching可以在不增加 TTFT 的情况下提高吞吐量。误区二：PD 分离部署但网络带宽不足典型表现：实现了 PD 分离架构，但 Prefill 节点和 Decode 节点之间使用了低带宽网络（如 25GbE或 100GbE TCP），KV Cache 传输延迟抵消了 PD 分离的收益。

反例：某企业使用 100GbE TCP 网络连接 Prefill 和 Decode 节点。70B 模型、4K tokens 输入的 KVCache 约 1.25GB，通过 100GbE TCP（有效吞吐约 10GB/s）传输需要约 125ms。加上调度开销，总 KVCache 传输延迟约 150-200ms——这比混合部署时的 Prefill-Decode 切换延迟（约 10-20ms）高了 10倍，导致 TTFT 反而增加了。正确做法：PD 分离必须配合高带宽低延迟网络。最低要求：InfiniBandNDR（400Gbps）或 RoCE v2 200GbE。

如果网络条件不满足，PD分离的收益可能为负。在无法升级网络的情况下，可以考虑将 Prefill 和 Decode部署在同一台服务器的不同 GPU 上（通过 NVLink 传输 KV Cache）。误区三：量化推理不做质量评估，直接上线典型表现：为了提升推理速度或减少显存占用，直接将模型量化到 INT4 并上线，没有进行系统的质量评估。结果模型在某些任务上的效果大幅下降，但问题不容易被发现（因为大部分请求的效果没有明显变化）。反例：某企业将 72B 模型从 FP16 量化到 INT4（GPTQ），显存从 144GB 降到36GB，推理速度提升了 2.5 倍。

上线后大部分指标正常，但在一周后被用户投诉"数学题和逻辑推理能力明显下降"。经排查发现，INT4 量化在需要精确计算的任务上精度损失达15-20%（因为量化误差在数值计算中被放大）。正确做法：量化上线前必须在完整的 eval set 上进行质量对比测试，特别关注数值计算、逻辑推理、代码生成等对精度敏感的任务。对于精度敏感的场景，使用 INT8 或 FP8 而非 INT4。建立量化的 A/B测试流程——量化版本先在小流量上运行，对比关键业务指标。误区四：训练时不使用 Gradient Checkpointing，显存不足后盲目减小 batch size典型表现：训练大模型时遇到 OOM（Out of Memory），第一反应是减小 batch size，而不是启用Gradient Checkpointing。

结果 batch size 减小到 1，训练效率极低。反例：某团队在 8 × A100 80GB 上微调 70B 模型，使用 ZeRO-3，初始 batch_size=8 时OOM。团队将 batch_size 逐步减小到 4、2、1，最终 batch_size=1 可以运行，但训练速度只有预期的1/8。后来有人建议启用 Gradient Checkpointing，在 batch_size=8 下成功运行，训练速度是 batch_size=1的 6 倍（虽然 Gradient Checkpointing 增加了 25% 的计算开销，但 batch_size 从 1 提升到 8带来的效率提升远大于此）。

正确做法：大模型训练时默认启用 Gradient Checkpointing。OOM时的优化优先级：（1）启用 Gradient Checkpointing（减少 50-70% 激活值显存）；（2）增大 ZeRO阶段（ZeRO-2 → ZeRO-3）；（3）使用混合精度（FP32 → BF16）；（4）使用 gradient accumulation保持等效 batch size 的同时减小实际 batch size；（5）最后才考虑减小模型规模或使用 LoRA。误区五：忽视 MFU 指标，只看 GPU 利用率典型表现：监控中显示 GPU 利用率 > 90%，认为训练效率很好。

但实际上 MFU（Model FLOPsUtilization）可能只有 30-40%，意味着大量算力被浪费在通信、内存访问等开销上。反例：某团队在 64 张 A100 上训练一个 30B 模型，GPU 利用率显示 92%，看起来很好。但计算MFU 后发现只有 35%——理论峰值算力 = 64 × 312 TFLOPS = 19,968 TFLOPS，实际训练吞吐量 = 45,000tokens/s，每 token 的 FLOPs ≈ 6 × 30B = 1.8 × 10，实际 FLOPs/s = 45,000 × 1.8 × 10 = 8.1 ×10 FLOPs/s = 8,100 TFLOPS，MFU = 8,100 / 19,968 = 40.6%。

进一步排查发现，60%的算力浪费在跨机通信上——因为 PP=8 跨了 8 台服务器，但 InfiniBand 只配置了 200Gbps（而非推荐的400Gbps NDR），通信成为严重瓶颈。正确做法：训练监控必须关注 MFU 而非 GPU 利用率。MFU的目标值：> 50% 为合格，> 60% 为良好，> 70% 为优秀。MFU 低于 50%时必须排查原因——通常是通信瓶颈（网络带宽不足、并行策略不合理）或数据加载瓶颈（存储 I/O不足）。误区六：MoE 模型使用与 Dense 模型相同的并行策略典型表现：将 MoE 模型（如 Mixtral 8×7B）像 Dense模型一样部署，没有使用专家并行（EP），导致所有 GPU都持有所有专家的完整副本，显存浪费严重。

反例：某团队使用 8 张 A100 部署 Mixtral 8×7B（46.7B 参数），使用 TP=8 的并行策略。TP=8意味着每张 GPU 持有模型的 1/8 参数——但 MoE层的专家不能简单地按张量切分（每个专家是一个独立的 FFN），TP 切分导致每个专家被拆分到 8 张GPU 上，AllReduce 通信量翻倍。同时由于路由机制的存在，不同 token 需要不同的专家，TP无法有效利用稀疏性。最终训练效率只有预期的 40%。正确做法：MoE 模型应该使用 TP + EP的混合并行策略——Attention 层使用 TP（在 NVLink 域内），MoE 层使用 EP（专家分布在不同 GPU上）。

对于 Mixtral 8×7B 在 8 卡上，推荐 TP=2（Attention 层）+ EP=4（8 个专家分布在 4 组 GPU上）或 TP=1 + EP=8（纯专家并行）。

### 3.7.7 优化方法论总结：从指标到行动的闭环

推理和训练优化不是零散的技巧堆砌，而是一个系统化的方法论。以下是经过验证的优化闭环：第一步：建立基线指标。在优化之前，必须先建立完整的性能基线。推理服务：测量 TTFT（P50/P95/P99）、TPOT（P50/P95/P99）、吞吐量（tokens/s/GPU）、最大并发数、显存使用率。训练任务：测量 tokens/s、MFU、通信/计算比、checkpoint 保存时间、GPU 利用率、网络带宽利用率。基线测量必须在标准负载下进行（固定的模型、固定的请求分布、固定的硬件配置），确保后续优化效果可对比。第二步：识别瓶颈层级。

根据基线指标，判断瓶颈在哪个层级：（1）如果是compute-bound（GPU 算力利用率 > 80%，但吞吐量不够）→考虑模型量化、模型蒸馏、更高效的模型架构；（2）如果是 memory-bound（显存带宽利用率 >80%，GPU 算力利用率 < 50%）→ 考虑 KV Cache 优化、batch size 调优、显存更大的GPU；（3）如果是 communication-bound（通信时间占比 > 30%）→考虑优化并行策略、升级网络带宽、优化 NCCL 配置；（4）如果是 IO-bound（数据加载时间占比 >20%）→ 考虑升级存储系统、优化数据预处理 pipeline、使用数据缓存。

第三步：选择 ROI 最高的优化手段。将所有可行的优化手段按"预期收益 /实施成本"排序，优先实施 ROI 最高的。例如：启用 Flash Attention（收益：Attention 加速 4-5倍，成本：修改几行代码）的 ROI 远高于更换 GPU 型号（收益：算力提升50%，成本：数百万元采购费用）。第四步：验证和迭代。每次优化后重新测量指标，与基线对比，确认优化效果。如果效果不及预期，分析原因并调整方案。优化是一个持续迭代的过程——随着模型规模增长、业务需求变化、硬件代际更新，优化策略也需要相应调整。优化效果参考表（按 ROI 排序）：本章核心要点总结：大模型推理和训练优化是一个系统工程，需要从算法（PD 分离、KV Cache管理、MoE 优化）、框架（vLLM/TensorRT-LLM/SGLang 选型）、硬件（GPU型号、互联带宽、显存容量）三个维度综合考虑。

PD分离是当前最有效的推理架构优化，但需要高带宽网络支撑；三级 KV Cache 体系可以将有效 KVCache 容量扩展 10-100 倍；MoE 模型需要专门的专家并行策略。训练优化的核心是提升MFU——通过 3D 并行、Flash Attention、混合精度等技术最大化有效算力利用率。所有优化都应该以量化指标（TTFT、TPOT、吞吐量、MFU）为指导，建立从指标测量到瓶颈定位到优化实施到效果验证的完整闭环。避免凭感觉调参，用数据说话。
